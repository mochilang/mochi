## Abstract

Mochi today (May 2026) integrates with Go, Python, TypeScript, and Rust ecosystems via typed FFI bridges. None of the four reaches .NET. The NuGet registry at nuget.org hosts 350,000+ packages (May 2026), including the dominant .NET libraries for JSON, logging, ORM, HTTP, serialization, cloud SDK access, and cryptography. A Mochi program cannot consume Newtonsoft.Json, Serilog, Dapper, Polly, Entity Framework Core, or any Azure/AWS/GCP .NET SDK. A Mochi package author cannot publish their work to NuGet where the existing .NET community can `dotnet add package` it.

MEP-68 specifies the **bidirectional .NET NuGet bridge**: Mochi packages can consume any NuGet package via `import dotnet "<package>@<semver>" as <alias>` with no user-written interop boilerplate, and Mochi packages can publish to nuget.org as .NET class libraries via `mochi pkg publish --to=nuget.org`. The bridge is the fifth source-language interop story Mochi ships (after Go, Python, TypeScript, and Rust), and the first one targeting the C#/.NET ecosystem, which remains the primary development platform for enterprise line-of-business software, Azure-based microservices, game tooling (Unity), and high-performance Windows applications.

The proposal builds on MEP-57's manifest/lockfile/capability infrastructure and MEP-53's emit pipeline, adds a self-contained component under `package3/dotnet/`, and introduces `dotnet` as a new `<lang>` token in the grammar's FFI-import production. The Mochi build pipeline gains one new target (`TargetDotnetLibrary`). The lockfile gains one new repeated table (`[[dotnet-package]]`). No existing transpiler MEP needs to change.

The system is anchored on seven load-bearing decisions, each justified in §Rationale and surveyed in the companion research notes:

1. **ECMA-335 CLI metadata as the canonical .NET assembly API surface.** Every .NET assembly (`.dll`) is a PE binary carrying a CLI metadata section defined by ECMA-335, the open ISO/IEC 23271 standard. This section encodes all public types, methods, properties, events, and generic parameters in a compact binary table format that Go can parse without invoking the .NET runtime. The bridge implements a Go-native ECMA-335 reader (`package3/dotnet/metadata/`) that walks the TypeDef, MethodDef, FieldDef, PropertyDef, ParamDef, and TypeSpec metadata tables, decodes type signatures from the #Blob heap, and correlates items with their XML documentation comments (`.xml` files bundled in `.nupkg` archives). This is analogous to MEP-73's use of rustdoc JSON for Rust, and analogous to how Go's `go/types` parser uses the exported symbol tables embedded in compiled Go packages. Parsing the C# source directly is rejected (not present in binary NuGet packages, and Roslyn would be required as a Go FFI dep). Using Roslyn's `Microsoft.CodeAnalysis` NuGet package in a bundled inspector tool is rejected for the primary path (would require shipping a platform-specific .NET binary with mochi; see rejected alternative #1). See [[01-language-surface]] §2, [[04-assembly-metadata-ingest]] §1, [[02-design-philosophy]] §1.

2. **NativeAOT `[UnmanagedCallersOnly]` wrapper project per imported .NET package, compiled to a static native library.** For each NuGet package the user imports, the bridge generates a sibling C# class library project (`dotnet_wrap/<package>/`) that references the source package and exposes `[UnmanagedCallersOnly]` extern functions wrapping each translatable public item: value types are passed by value over the C ABI, reference types (class, string, arrays) become opaque `IntPtr` handles tracked by a per-process `GCHandleTable` (pinned `GCHandle.Alloc` for structs, normal `GCHandle.Alloc` for classes), `string` becomes `byte*` (UTF-8, null-terminated) with an explicit `mochi_dotnet_<pkg>_string_free` export, `List<T>` becomes a `(ptr, len, cap)` `[StructLayout]` struct with a `_free` export, `Task<T>` and `ValueTask<T>` are awaited synchronously via `.GetAwaiter().GetResult()` in a detached thread pool context that avoids sync-context deadlocks, and `Nullable<T>` becomes a two-field `(value, has_value)` struct at the ABI. The wrapper project is published with `dotnet publish -r <rid> /p:PublishAot=true /p:NativeLib=Static` to produce a `.a` / `.lib` static archive, which the MEP-53 build driver links into the Mochi binary via `cargo:rustc-link-lib=static`. NativeAOT (stable since .NET 8, November 2023) compiles the entire .NET dependency graph to native machine code ahead-of-time, eliminating the JIT and the CoreCLR hosting overhead. An alternative fallback path using CoreCLR runtime hosting (`coreclr_initialize`) is reserved for phase 13 for packages that are NativeAOT-unfriendly. See [[02-design-philosophy]] §2, [[03-prior-art-bridges]] §3, [[09-abi-stability]] §1.

3. **Closed .NET-to-Mochi type translation table, with explicit refusal on out-of-table cases.** The translation covers: `int↔int`, `long↔long`, `float↔float`, `double↔float` (widening), `decimal↔decimal` (128-bit via a two-word struct), `string↔string` (by copy across UTF-8 boundary), `bool↔bool`, `char↔int` (Unicode codepoint), `byte↔byte`, `sbyte↔int`, `short↔int`, `ushort↔int`, `uint↔long`, `ulong↔long`, `void↔unit`, `T?` (nullable value type) `↔ T|nil`, `Nullable<T>↔T|nil`, `List<T>↔list<T>` (when T is in-table), `IList<T>↔list<T>`, `IEnumerable<T>↔list<T>` (materialised), `Dictionary<K,V>↔map<K,V>` (when K is string or integer), `IDictionary<K,V>↔map<K,V>`, `HashSet<T>↔set<T>`, `SortedDictionary<K,V>↔omap<K,V>`, `Task<T>↔async T` (awaited via GetAwaiter().GetResult()), `ValueTask<T>↔async T`, `Task↔async unit`, `enum` (integer-backed) `↔ mochi enum`, `class` / `record` (concrete, no generics) `↔ mochi record`, `sealed class` hierarchy (discriminated union pattern) `↔ mochi ADT`, `interface` (single implementation bound) `↔ mochi interface`. Items outside the table (raw pointers `void*`/`T*`, `ref`/`out`/`in` parameters of non-value types, `Span<T>`, `Memory<T>`, `ReadOnlySpan<T>`, `dynamic`, `object` (untyped), unmanaged generic constraints `where T : unmanaged`, `delegate` with multi-cast, COM interop types, `IAsyncEnumerable<T>`, and generic type parameters beyond the monomorphised concretisations declared in `mochi.toml`'s `[dotnet.monomorphise]` section) are skipped with a `SkipReport` entry naming the item and the reason. See [[05-type-mapping]] §1, [[02-design-philosophy]] §3.

4. **`import dotnet "<package>@<semver>" as <alias>` as the sole surface keyword.** The grammar gains exactly one new lexeme: the keyword `dotnet` admitted as a `<lang>` in the existing `import <lang> "<spec>" as <alias>` production. The `<spec>` forms are: `<package-id>` (bare, resolved through `[dotnet-dependencies]`), `<package-id>@<semver-req>`, `<package-id>@git+<url>#<commit>`, and `<package-id>@path+<relative>`. The `mochi.lock` records the resolved version (four-part .NET version normalised to SemVer-2 form), BLAKE3-256 + SHA-256 of the `.nupkg` archive, the CLI metadata snapshot SHA-256, and the NativeAOT wrapper SHA-256. No other Mochi syntax changes; `import dotnet` participates in the same module-resolution flow as `import go`, `import python`, `import typescript`, and `import rust`. See [[01-language-surface]] §1, [[06-nuget-publish-flow]] §2.

5. **Mochi → .NET class library emission via `TargetDotnetLibrary`.** MEP-53 gains a new emit target. Where `TargetRustLibrary` (MEP-73) emits `src/lib.rs`, `TargetDotnetLibrary` emits `Src/<PackageName>.cs` with `public static` functions, `public record` types, and sealed class hierarchies mirroring the Mochi package's public surface; writes a `.csproj` with `<OutputType>Library</OutputType>`, `<TargetFramework>net9.0</TargetFramework>`, and publish metadata; writes an XML documentation file; populates `.nuspec` metadata from `mochi.toml`'s `[package]` section; and emits a `global.json` pinning the SDK version. When `[dotnet.publish] nativeaot = true` is set, the library additionally exposes `[UnmanagedCallersOnly]` entry points so non-.NET consumers can link against it. See [[01-language-surface]] §3, [[06-nuget-publish-flow]] §1.

6. **NuGet trusted publishing via GitHub Actions OIDC, no API key path.** When `mochi pkg publish --to=nuget.org` runs, the bridge: (a) emits the .NET class library project via `TargetDotnetLibrary`; (b) packs it via `dotnet pack`; (c) obtains an OIDC token from the CI environment (GitHub Actions `id-token: write`, GitLab CI, Azure Pipelines); (d) exchanges the token with nuget.org's trusted publisher endpoint (GA November 2024, available on all nuget.org packages); (e) nuget.org validates the token against the registered repository/workflow constraint; (f) uploads the signed `.nupkg`. Long-lived nuget.org API keys (`NUGET_API_KEY`) are not supported (matches MEP-57's principle that long-lived tokens are deprecated; the nuget.org trusted publishing GA in 2024 makes this position tenable for new tooling). `--dry-run` skips upload but exercises the pack and sign flow against a mock nuget server. See [[07-oidc-nuget-trusted-publishing]] §1, [[02-design-philosophy]] §5.

7. **Async bridge via `Task<T>.GetAwaiter().GetResult()` executed on a dedicated CLR ThreadPool thread to avoid sync-context deadlock.** .NET async code (`async Task<T>`) is idiomatic in virtually every modern .NET library (HttpClient, Entity Framework, System.IO.Pipelines, SignalR). Calling `.GetAwaiter().GetResult()` directly on a calling thread that holds a SynchronizationContext (e.g., a WPF dispatcher or ASP.NET request context) deadlocks. The wrapper generates each async-fn bridge as: (1) marshal arguments into the GCHandle table; (2) post the continuation to `ThreadPool.QueueUserWorkItem`; (3) block the calling thread on a `ManualResetEventSlim` until the continuation completes; (4) unmarshal the result. This guarantees no deadlock regardless of caller context (the work runs on a pool thread that has no sync context). The pattern is more complex than MEP-73's `tokio::block_on` but handles the same fundamental impedance mismatch. `IAsyncEnumerable<T>` (async streams) is excluded from the v1 translation table (skipped with `SkipReport`) and deferred to a phase 11 extension. See [[08-async-bridge]] §1, [[02-design-philosophy]] §4.

The gate for each delivery phase is empirical: the bridge must successfully ingest a curated 25-package fixture corpus (drawn from the May 2026 nuget.org most-downloaded snapshot: Newtonsoft.Json, Microsoft.Extensions.DependencyInjection, Microsoft.Extensions.Logging, Microsoft.Extensions.Configuration, Serilog, AutoMapper, FluentValidation, MediatR, Polly, RestSharp, Dapper, StackExchange.Redis, Grpc.Core, Microsoft.EntityFrameworkCore, Microsoft.Data.SqlClient, Npgsql, MongoDB.Driver, RabbitMQ.Client, NATS.Client.Core, CsvHelper, YamlDotNet, Markdig, BCrypt.Net-Next, SixLabors.ImageSharp, Humanizer) for phases 1-8; generate a translatable surface for every public item the closed type-table covers; emit a `SkipReport` for every out-of-table item; produce a Mochi `extern fn` corpus that parses cleanly; and build the resulting NativeAOT-wrapper-plus-Mochi binary via MEP-53's existing build path. A separate publish gate exercises `TargetDotnetLibrary` against an in-tree mock NuGet server, asserts the published package `dotnet add package`s cleanly into a downstream .NET project, and asserts that the OIDC token verification flow passes against a mock nuget.org endpoint.

## Motivation

Mochi today (May 2026) integrates with four foreign ecosystems: Go (via `import go "..."`), Python (via `import python "..."`), TypeScript/Deno (via `import typescript "..."`), and Rust (via MEP-73's `import rust "..."`). All four are covered. The one large typed ecosystem not yet bridged is .NET. The omission is costly for six overlapping reasons:

1. **The NuGet ecosystem is the canonical runtime for enterprise backends, cloud-native Azure workloads, and game tooling.** nuget.org hosts 350,000+ packages (May 2026); the top 25 packages by download count collectively exceed 150 billion lifetime downloads. Microsoft.Extensions.DependencyInjection, Microsoft.Extensions.Logging, System.Text.Json, and Newtonsoft.Json are each pulled into virtually every .NET build in the industry. Azure SDK for .NET (`Azure.*`), AWS SDK for .NET (`AWSSDK.*`), and Google Cloud Client Libraries for .NET (`Google.Cloud.*`) provide the primary entrypoints to the three dominant cloud platforms. A Mochi program needing blob storage, a SQL database, a message queue, or HTTP resilience policies needs .NET to reach these SDKs.

2. **Unity game tooling runs on C#/.NET.** The Unity Editor plugin ecosystem, the DOTS ECS runtime, the Unity Addressables system, and most asset pipeline tools publish their APIs as NuGet packages or Unity Package Manager packages that wrap NuGet. A Mochi script running inside a Unity Editor plugin requires interop with these APIs.

3. **The .NET ecosystem expects class libraries as the distribution unit.** When a Mochi package author writes a generally useful library, publishing a `.nupkg` to nuget.org puts it in front of the 6+ million active .NET developers (Microsoft Build 2025 keynote estimate). MEP-53 emits Rust source; it does not emit a `.csproj`. MEP-68 fills that gap.

4. **NativeAOT is production-ready and eliminates the JIT/GC-startup cost.** .NET 8 (November 2023) shipped NativeAOT as a supported production feature. `dotnet publish /p:PublishAot=true` produces a self-contained native binary with no CoreCLR host overhead, startup times under 5ms (vs. 100-300ms for JIT-warmed .NET), and deterministic memory layout. For a bridge that links a .NET library into a Mochi binary, NativeAOT is the right tool: no separate process, no CoreCLR hosting API, no JIT interferences at call boundaries.

5. **NuGet trusted publishing GA (November 2024) makes token-free publishing the default for new tooling.** nuget.org's trusted publishing endpoint (GitHub Actions OIDC, GitLab CI, Azure Pipelines) went GA in November 2024. Any tooling designed after that date that ships a long-lived API key path is shipping a security regression.

6. **ECMA-335 is a stable, open, machine-readable .NET assembly description.** Unlike Python (ctypes require `.pyi` stubs), unlike Rust (pre-MEP-73, before rustdoc JSON stabilisation), .NET assemblies embed their complete type system in the binary format from day one. The bridge reads these tables directly in Go; no runtime, no SDK, no external tool invocation is required for the type-extraction step. This makes `mochi pkg lock` deterministic and air-gap-compatible.

## Specification

This section is normative. Sub-notes under [/docs/research/0068/](/docs/research/0068/) are informative.

### 1. Pipeline overview

MEP-68 introduces a per-import .NET dependency resolution layer between the Mochi parser (after MEP-57 has resolved `mochi.toml`) and the MEP-53 build driver:

```
mochi.toml [dotnet-dependencies]
   |  pkgmanifest.Parse + pkgsolver.Solve (MEP-57)
   v
resolved .NET dep tree (package id + version + source URL)
   |  package3/dotnet/nuget.Fetch (NuGet V3 registration + download)
   v
.nupkg archives in ~/.cache/mochi/dotnet-deps/<blake3-hex>/
   |  package3/dotnet/metadata.Parse (ECMA-335 CLI metadata reader)
   v
PublicSurface + XMLDoc per assembly per package
   |  package3/dotnet/typemap.Translate (closed .NET-to-Mochi table)
   v
TranslatedSurface + SkipReport per package
   |  package3/dotnet/nativeaot.Emit (NativeAOT wrapper C# project generator)
   v
dotnet_wrap/<package>/ C# class library project
   |  package3/dotnet/externemit.Emit (Mochi extern fn / extern type)
   v
synthesised .mochi shim file per package
   |  MEP-53 Driver.Build (TargetNativeExecutable / TargetDotnetLibrary)
   v
binary or .NET class library crate
```

The bridge does not invoke the .NET runtime at type-extraction time. ECMA-335 parsing is done entirely in Go at `mochi pkg lock` time. The NativeAOT wrapper project is compiled by `dotnet publish` (invoked by `Driver.Build`), which is the only .NET SDK invocation; the user's Mochi build orchestrates it.

### 2. Manifest extension: `[dotnet-dependencies]` and `[dotnet]`

The MEP-57 `mochi.toml` gains two new optional top-level tables:

```toml
[dotnet-dependencies]
"Newtonsoft.Json" = "^13.0"
"Serilog" = { version = "^3.1", include-assets = "all" }
"Dapper" = "^2.1"
"Microsoft.EntityFrameworkCore" = { version = "^9.0", assets = ["compile", "runtime"] }
"MyLocalLib" = { path = "../MyLib/MyLib.csproj" }
"MyGitLib" = { git = "https://github.com/example/mylib", commit = "abc123" }

[dotnet]
framework = "net9.0"
runtime-identifiers = ["linux-x64", "linux-arm64", "osx-arm64", "win-x64"]
nullable = true
monomorphise = [
    { item = "Newtonsoft.Json.JsonConvert.DeserializeObject", T = "MyRecord" },
]

[dotnet.publish]
nativeaot = true
native-lib = "Static"
cbindgen-header = false

[dotnet.capabilities]
net = true
fs = false
proc = false
unsafe = false
```

`[dotnet-dependencies]` follows NuGet's package reference grammar: bare string for version constraint (SemVer-2 range syntax: `^13.0`, `~3.1`, `>=9.0.0`, `[9.0.0]`), table form for additional NuGet-specific knobs (`include-assets`, `assets`, `path`, `git`, `commit`). The bridge synthesises the wrapper project's `.csproj` `<PackageReference>` entries from this table.

The `[dotnet]` table holds Mochi-specific knobs:

- `framework`: the target framework moniker (TFM) for the wrapper project and the emitted library. Default `"net9.0"` (NativeAOT-stable, ships with .NET 9 LTS). `"net8.0"` is the minimum NativeAOT-capable TFM.
- `runtime-identifiers`: the list of .NET runtime identifiers for which to compile the NativeAOT wrapper. Default `["linux-x64", "linux-arm64", "osx-arm64", "win-x64"]` (matches MEP-53's four primary targets). Each RID triggers a separate `dotnet publish` invocation.
- `nullable`: whether to enable C# nullable reference types (`<Nullable>enable</Nullable>`) in the wrapper project. Default `true`.
- `monomorphise`: explicit generic instantiations. For each entry, the bridge emits the NativeAOT wrapper for `<item><T>` rather than emitting a `SkipReport`.

The `[dotnet.publish]` table holds Mochi-as-library knobs:

- `nativeaot`: whether `TargetDotnetLibrary` also emits `[UnmanagedCallersOnly]` entry points and sets `/p:PublishAot=true` (so non-.NET callers can link against the static lib). Default `false`.
- `native-lib`: the `<NativeLib>` MSBuild property value. `"Static"` for a `.a`/`.lib` archive, `"Shared"` for a `.so`/`.dylib`/`.dll`. Default `"Static"`.
- `cbindgen-header`: whether to emit a C header alongside the native output for non-.NET/non-Mochi consumers. Default `false`.

The `[dotnet.capabilities]` table holds .NET-bridge-specific capability flags (a refinement of MEP-57's `[capabilities]` table; a capability set here that contradicts the parent `[capabilities]` declaration is a manifest validation error):

- `net`: the package dep graph opens network connections (HttpClient, SqlClient, Redis, gRPC). Default `false`.
- `fs`: the dep graph reads or writes files (System.IO, FileStream). Default `false`.
- `proc`: the dep graph spawns processes (System.Diagnostics.Process). Default `false`.
- `unsafe`: the dep graph contains items wrapped with a hand-authored `extern fn ... from dotnet "..."` bypass declaration. Default `false`.

### 3. Lockfile extension: `[[dotnet-package]]`

The MEP-57 `mochi.lock` gains one new repeated table:

```toml
[[dotnet-package]]
id = "Newtonsoft.Json"
version = "13.0.3"
source = { kind = "registry", registry = "https://api.nuget.org/v3/index.json" }
nupkg-blake3 = "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
nupkg-sha512 = "fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210"
metadata-sha256 = "aabbcc..."
wrapper-sha256 = "ddeeff..."
capabilities-declared = ["net"]
target-framework = "net9.0"
dependencies = ["Microsoft.CSharp@>=4.7.0"]
```

`nupkg-blake3` and `nupkg-sha512` are the integrity hashes of the `.nupkg` archive. BLAKE3-256 is the primary verification hash (matching MEP-57's dual-hashing rule). SHA-512 matches the hash NuGet V3's package content endpoint publishes (`packageHash` field in the registration blob).

`metadata-sha256` records the SHA-256 of the ECMA-335 metadata snapshot the bridge extracted at lock time. A drift here (e.g., the package was republished with a patched assembly—which nuget.org normally prevents but can happen for floating-version sources) at `mochi pkg lock --check` time is a hard error.

`wrapper-sha256` records the SHA-256 of the synthesised NativeAOT wrapper project's `Src/Wrapper.cs`. A drift at `--check` time is a hard error.

`capabilities-declared` is the capability set the manifest declared at lock time. A capability addition from a transitive dep update at `--check` time is a hard error pending re-acknowledgement (MEP-57 monotonicity rule).

`target-framework` records the TFM at lock time so a `--check` on a different SDK installation (which might resolve a higher TFM) is a hard error.

`dependencies` records the resolved transitive dependency list (package id + version range) so the full dep graph is reproducible from the lockfile alone.

### 4. Surface syntax: `import dotnet "..."`

The Mochi grammar's existing FFI-import production:

```
ImportStmt := "import" Lang? StringLit "as" Ident ("auto")?
Lang := "go" | "python" | "typescript" | "rust" | "dotnet"
```

gains `dotnet` as a `Lang` alternative. The string literal forms:

| Form | Resolution |
|------|------------|
| `<package-id>` | Bare name, resolves through `[dotnet-dependencies]` + `mochi.lock` |
| `<package-id>@<semver-req>` | Explicit version constraint (`^13.0`, `[13.0.3]`, `>=8.0,<10.0`) |
| `<package-id>@git+<url>#<commit>` | Git source pinned to commit or tag |
| `<package-id>@path+<rel-path>` | Path source relative to mochi.toml |

Example surface programs:

```mochi
import dotnet "Newtonsoft.Json@^13.0" as Json
import dotnet "Polly" as Polly
import dotnet "Dapper" as Dapper

fn fetch_users(conn: DbConnection): list<User> {
    return Dapper.Query(conn, "SELECT * FROM users")
}

fn resilient_get(url: string): string {
    let policy = Polly.Policy.Handle(HttpRequestException).Retry(3)
    return policy.Execute(fn() { Http.get(url) })
}
```

The `<alias>` introduces a Mochi namespace; `<alias>.<Item>` resolves to the synthesised `extern fn` or `extern type` the bridge generated for `<PackageId>.<Item>`. Type names follow the C# naming convention (PascalCase); method names are mapped 1:1 from C# PascalCase to the same PascalCase in Mochi (the bridge does not rename; Mochi users interoperating with .NET are expected to know PascalCase .NET names).

The `auto` modifier is admitted for `import dotnet ... auto`, binding every public top-level item of the package at file scope rather than namespaced under the alias. Default is namespaced.

### 5. CLI surface

The Mochi CLI gains the following additions under `mochi pkg`:

- `mochi pkg add dotnet <PackageId>[@<semver>]`: adds to `[dotnet-dependencies]` and runs `mochi pkg lock`.
- `mochi pkg lock`: extended to walk `[dotnet-dependencies]`, query the NuGet V3 registration endpoint for version resolution, fetch `.nupkg` archives into the content-addressed cache, run ECMA-335 CLI metadata ingest, synthesise the NativeAOT wrapper project, and write `[[dotnet-package]]` entries.
- `mochi pkg lock --check`: verifies `nupkg-blake3`, `metadata-sha256`, `wrapper-sha256`, and `capabilities-declared` for every `[[dotnet-package]]` entry.
- `mochi pkg publish --to=nuget.org [--dry-run]`: emits `TargetDotnetLibrary`, runs `dotnet pack`, obtains a CI OIDC token, exchanges it with nuget.org's trusted-publishing endpoint, uploads the `.nupkg`.
- `mochi pkg sync dotnet`: regenerates the NativeAOT wrapper project from scratch without changing the lockfile. Used after manual edits to the shim file.

### 6. Build orchestration

When a Mochi program contains one or more `import dotnet "..."` declarations, the MEP-53 build driver gains:

1. Before invoking `cargo build`, the driver calls `package3/dotnet/Bridge.PrepareWorkspace(workdir, mochiLock)` which:
   - For each `[[dotnet-package]]` in `mochi.lock`, materialises the `.nupkg` into `<workdir>/dotnet_deps/<id>.<version>/`.
   - Materialises the synthesised wrapper project into `<workdir>/dotnet_wrap/<id>/`.
   - Writes a `<workdir>/NuGet.Config` that points `<add key="localPackages" value="...dotnet_deps/"/>` as a local NuGet feed so the wrapper project's `dotnet restore` resolves from the content-addressed cache.
   - The main Mochi package's emitted Rust source gains `#[link(name = "<id>_dotnet_wrap", kind = "static")]` directives for each wrapper static lib.

2. The MEP-53 emit pass treats each `import dotnet "<package>" as <alias>` as a Mochi `import "./dotnet_wrap/<id>/shim.mochi" as <alias>` shim.

3. For each runtime identifier in `[dotnet] runtime-identifiers`, `Driver.Build` invokes `dotnet publish <workdir>/dotnet_wrap/<id>/<id>.csproj -r <rid> /p:PublishAot=true /p:NativeLib=Static -c Release --output <workdir>/dotnet_native/<rid>/`.

4. The linker step adds `-L <workdir>/dotnet_native/<host-rid>/` and `-l <id>_dotnet_wrap` (plus any system libraries NativeAOT requires: `-lc`, `-lm`, `-lpthread`, `-ldl`, `-lstdc++` on Linux; `-framework Foundation -framework Security` on macOS).

5. The driver invalidates the cache when any `[[dotnet-package]]` `wrapper-sha256` changes.

### 7. Async bridge

The NativeAOT wrapper for a method returning `Task<T>` or `ValueTask<T>` generates the following pattern in C#:

```csharp
[UnmanagedCallersOnly(EntryPoint = "mochi_dotnet_<pkg>_<ClassName>_<MethodName>")]
public static unsafe <C_T> <pkg>_<ClassName>_<MethodName>(<C_args>) {
    var mre = new ManualResetEventSlim(false);
    <C_T> result = default;
    Exception? error = null;
    ThreadPool.QueueUserWorkItem(_ => {
        try {
            result = MarshalResult(<ClassName>.<MethodName>(<args>).GetAwaiter().GetResult());
        } catch (Exception ex) {
            error = ex;
        } finally {
            mre.Set();
        }
    });
    mre.Wait();
    if (error != null) MochiThrowException(error);
    return result;
}
```

The `ThreadPool.QueueUserWorkItem` dispatch ensures the `.GetAwaiter().GetResult()` call runs on a thread with no SynchronizationContext, preventing the ASP.NET-style deadlock that a naive `task.Result` access on the calling thread would cause. `ManualResetEventSlim` is used (not `SemaphoreSlim.WaitAsync`) because the calling thread is a native C thread managed by the Mochi/Rust runtime, not a CLR-managed thread.

`IAsyncEnumerable<T>` is excluded from the v1 translation (skipped with `SkipReport: IAsyncEnumerable<T> requires a streaming bridge not yet implemented`). A phase 11 extension will add an async streaming bridge using a Go-style channel at the C ABI boundary.

### 8. GC handle table

.NET reference types (class instances, strings, arrays) cannot be passed directly across the C ABI because the .NET GC may move objects in memory. The wrapper uses the `GCHandle` mechanism:

- For each public property or method that returns a reference type, the wrapper wraps the return value with `GCHandle.Alloc(obj, GCHandleType.Normal)` and returns a `nint` (native integer) handle.
- The Mochi side stores the handle as an opaque `extern type` (64-bit integer on all platforms).
- A synthesised `extern fn mochi_dotnet_<pkg>_<TypeName>_free(handle: nint): unit` calls `GCHandle.FromIntPtr(handle).Free()`.
- For types marked `[StructLayout(LayoutKind.Sequential)]` or `[StructLayout(LayoutKind.Explicit)]` with all fields in-table, the wrapper copies by value and no GC handle is needed.
- Strings are always copied to a `byte*` (UTF-8) buffer allocated with `Marshal.AllocHGlobal` and freed by a synthesised `mochi_dotnet_string_free`.

This strategy trades some allocation overhead for a clean ABI. The alternative of `GCHandleType.Pinned` would allow direct pointer access but is only valid for blittable value types and would expose GC internals to Mochi.

### 9. NativeAOT subset and fallback

NativeAOT (phase 0-12) covers the majority of popular NuGet packages. Packages that cannot be compiled with NativeAOT (packages that use `Assembly.Load`, `Activator.CreateInstance` with unknown types, `Expression.Compile`, `Emit`, MEF, XAML/WPF, ASP.NET Core hosting, or third-party IL-emitting libraries) generate a `NativeAOTCompatibility.Violation` entry in the `SkipReport` at lock time.

Phase 13 implements a fallback path for NativeAOT-incompatible packages using **CoreCLR hosting**: the Mochi binary embeds `coreclr_initialize` / `coreclr_create_delegate` from the CoreCLR shared library and loads the .NET runtime into the same process at startup. This path carries: a 100-300ms cold-start cost, a ~10MB coreclr binary dep, and GC/JIT non-determinism. It is opt-in per package via `[dotnet.capabilities] coreclr-hosting = true` and requires the user to acknowledge the trade-offs.

### 10. TargetDotnetLibrary: Mochi as NuGet package

When `Driver.LibraryMode = true` and `target = TargetDotnetLibrary`, the MEP-53 driver emits:

```
<workdir>/
  MyPackage.csproj          # <OutputType>Library</OutputType>, <TargetFramework>net9.0</TargetFramework>
  Src/
    MyPackage.cs            # public static class MyPackage { ... } with one public method per Mochi public fn
    MyPackage.Types.cs      # public record / sealed class hierarchy per Mochi public type
  MyPackage.xml             # XML documentation (/// <summary> from Mochi doc-comments)
  MyPackage.nuspec          # populated from mochi.toml [package] section
  global.json               # { "sdk": { "version": "<pinned>" } }

```

`MyPackage.cs` maps:

| Mochi surface | C# emission |
|---------------|-------------|
| `pub fn f(a: int, b: string): bool` | `public static bool F(int a, string b)` |
| `pub record Point { x: float, y: float }` | `public record Point(float X, float Y)` |
| `pub type Shape = Circle(float) \| Rect(float, float)` | `public abstract record Shape; public sealed record Circle(float R) : Shape; public sealed record Rect(float W, float H) : Shape;` |
| `pub type Color = Red \| Green \| Blue` | `public enum Color { Red, Green, Blue }` |
| `pub interface Drawable { fn draw(): unit }` | `public interface IDrawable { void Draw(); }` |

| `mochi.toml` | `.nuspec` |

| `name` | `<id>` |

| `authors` | `<authors>` |

The `.csproj` additionally sets `<GeneratePackageOnBuild>false</GeneratePackageOnBuild>` (the bridge calls `dotnet pack` explicitly) and `<PackageVersion>$(Version)</PackageVersion>` propagated from `mochi.toml`.

## Alternatives considered

1. **Bundle a NativeAOT-compiled `mochi-dotnet-inspect` binary for metadata extraction instead of the Go-native ECMA-335 parser.** A bundled inspector binary (like `cargo --output-format=json` for Rust) would be simpler to implement but would require platform-specific binaries in the mochi distribution (linux-x64, linux-arm64, osx-arm64, win-x64), complicating the release pipeline. The Go-native parser is about 2,000 LOC (PE header + CLI metadata tables + type signature decoder + XML doc parser) and is air-gap-compatible. Rejected in favour of the Go-native approach for the primary path; the inspector binary approach is an acceptable future optimisation if the Go parser proves maintenance-intensive.

2. **Use Roslyn (`Microsoft.CodeAnalysis`) as the bind source instead of ECMA-335 binary metadata.** Roslyn provides a rich semantic model over C# source and could extract generics, attributes, and partial classes in ways that binary metadata cannot. Rejected: Roslyn is only available when C# source is present; binary-only NuGet packages (packages shipping only DLLs without source link or Roslyn analyzers) would have no source for Roslyn to parse. Binary DLLs are the norm on nuget.org for commercial and legacy packages. ECMA-335 binary metadata is always present and is sufficient for the closed type table.

3. **Use P/Invoke (reverse-direction) instead of NativeAOT for the wrapper.** P/Invoke is a .NET mechanism for calling native C functions from .NET. MEP-68 is the other direction: Mochi (native) calling .NET code. P/Invoke cannot be the wrapper strategy; it is a .NET-side tool. The correct .NET primitive for exposing .NET to native callers is `[UnmanagedCallersOnly]`, which requires NativeAOT or `unsafe` function pointers in non-AOT contexts.

4. **Use `CppSharp` or `IKVM.NET` as the binding layer.** CppSharp generates C# bindings from C/C++ headers (wrong direction). IKVM.NET compiles Java bytecode to .NET (not relevant). Neither fits the use case.

5. **Use gRPC or a local Unix socket for cross-runtime communication.** A gRPC bridge would run the .NET package in a separate process and communicate via protobuf over a Unix domain socket. This approach has ~100µs per-call overhead (unsuitable for tight loops), requires a separate process lifecycle, and defeats the "no boilerplate" promise. Rejected; the NativeAOT in-process link path is the right choice for performance-sensitive code.

6. **Use `Microsoft.Extensions.Hosting` + `IHostedService` to embed CoreCLR and communicate via shared memory.** This is effectively the CoreCLR hosting path already covered in phase 13 as a fallback. For NativeAOT-compatible packages (the majority), it is unnecessary overhead.

7. **Use WIT (Wasm Interface Types) / wit-bindgen as the .NET binding layer.** WIT requires the .NET `componentize-dotnet` tool to generate Wasm Component model bindings. As of May 2026, componentize-dotnet is pre-GA and only covers a subset of .NET types. Deferred to a post-v1 extension that activates when the user sets `[dotnet.publish] wit = true`.

8. **Parse .NET 5+ `ref assemblies` (reference assemblies) instead of implementation assemblies.** Reference assemblies ship with the .NET SDK and contain only the public API surface (method signatures without bodies), making them smaller. However, NuGet packages for third-party libraries do not always ship reference assemblies; only the .NET BCL does reliably. The bridge targets implementation assemblies, which are universally present.

9. **Allow long-lived nuget.org API keys for the publish path.** Rejected: matches MEP-57's broader principle. NuGet trusted publishing GA November 2024 is the unambiguous 2025-2026 default for new tooling.

10. **Translate .NET value semantics (struct copy, readonly struct, ref struct) into Mochi.** Mochi does not have a value-vs-reference semantic distinction at the language level. The bridge translates all `struct` types that are in-table to Mochi `record` types (pass-by-copy at the C ABI boundary for blittable structs). Non-blittable structs (containing reference-type fields) are handled as GC-handle opaque types.

11. **Generate NuGet packages via `dotnet new` templates rather than direct file emission.** `dotnet new classlib` generates a `.csproj` that the bridge would then modify. Rejected: the bridge owns the project structure; template scaffolding introduces an indirect dependency on the `dotnet new` templates version that varies across SDK releases.

12. **Run `dotnet publish /p:PublishAot=true` at `mochi pkg lock` time (eager AOT compile).** Rejected: AOT compilation can take 30-120 seconds per package per RID. Deferring AOT to build time (consistent with how `cargo build --release` compiles the wrapper crate in MEP-73) keeps `mochi pkg lock` fast and allows developers to lock without the full .NET SDK installed.

## Risks

1. **NativeAOT compatibility rate.** Not all NuGet packages are NativeAOT-compatible. Packages that use `Assembly.Load`, `DynamicMethod.Emit`, `Expression.Compile`, MEF/MEF2, XAML/Avalonia with runtime XAML loading, or late-bound COM interop will fail to compile with `/p:PublishAot=true`. Mitigation: the bridge runs a lightweight NativeAOT-compatibility pre-check at `mochi pkg lock` time using the `ILLink.Descriptors` + `RequiresDynamicCodeAttribute` annotations present in .NET 8+ assemblies; packages that fail the pre-check are flagged and routed to the CoreCLR hosting fallback (phase 13) with a clear user-facing diagnostic.

2. **ECMA-335 schema complexity.** The ECMA-335 CLI metadata format has 40+ metadata tables, 15+ type signature kinds, and edge cases around generic instantiation, forwarded types, nested types, and extension methods. A Go-native parser that covers the full spec is ~2,000 LOC but requires careful testing. Mitigation: the fixture corpus gates each of the 25 packages individually; every metadata table path exercised by the corpus must parse cleanly before phase 2 is marked LANDED.

3. **NativeAOT compile time.** A NativeAOT compilation of `Newtonsoft.Json` + its deps produces ~8,000 LOC of synthesised C# and takes ~45 seconds on a warm cache (Apple M3) and ~120 seconds cold. For 10 .NET package imports, the NativeAOT pass dominates total build time. Mitigation: wrapper static libs are cached at `~/.cache/mochi/dotnet-deps/wrappers/<wrapper-sha256>-<rid>/`; only packages whose `wrapper-sha256` changed are recompiled.

4. **Four-RID AOT matrix.** `runtime-identifiers = ["linux-x64", "linux-arm64", "osx-arm64", "win-x64"]` means four separate `dotnet publish` invocations per package per build. Cross-compilation for non-host RIDs requires the .NET cross-compilation toolchain (`dotnet publish -r linux-arm64` on macOS needs the ARM64 linker, typically via `cargo-zigbuild`'s zig cc). Mitigation: `cargo-zigbuild` is already required by MEP-53; the bridge reuses it.

5. **GC handle leak.** If the Mochi program creates a GC handle via a .NET object return value but never calls the synthesised `_free` symbol (e.g., due to an early return on error), the `GCHandle` leaks and the object is never collected. Mitigation: the Mochi type system emits a `defer <alias>.<Type>_free(handle)` call at every scope exit where a GC handle is in scope (same strategy MEP-73 uses for Box<T> raw-pointer wrappers).

6. **NuGet trusted publishing GA coverage.** Not all nuget.org packages can receive trusted-publishing uploads yet; a user publishing a new crate must first configure the trusted publisher on nuget.org's package management UI. Mitigation: `mochi pkg publish --to=nuget.org` opens the nuget.org trusted publisher setup URL in the browser if the OIDC token exchange returns a 403 (not yet configured). A `--allow-apikey-fallback` escape hatch is provided during the nuget.org rollout period (default off; removed once GA is universally enforced).

7. **Generic monomorphization explosion.** A generic .NET type like `IEnumerable<T>` with many monomorphise entries produces a wrapper with many `[UnmanagedCallersOnly]` exports and a correspondingly long AOT compile. Mitigation: the `[dotnet.monomorphise]` table is explicit-only; the bridge never auto-monomorphises.

8. **Windows cross-compilation.** Cross-compiling a `win-x64` NativeAOT static lib from Linux or macOS requires the MSVC linker or the MinGW-w64 linker. NativeAOT on Windows uses `link.exe` (MSVC) by default; cross-compilation with MinGW-w64 is experimental as of .NET 9. Mitigation: `win-x64` cross-compilation is gated as `experimental` in phase 7; `win-x64` NativeAOT on a Windows host is the supported path.

9. **CoreCLR version skew in the fallback path.** The CoreCLR hosting fallback (phase 13) requires a matching `libcoreclr.so` at runtime. If the user's machine has a different .NET version than the one the bridge targeted, the runtime load may fail. Mitigation: the fallback path embeds the exact `libcoreclr` version in the Mochi binary (similar to how Go CGO links a specific glibc version) and records the version in `mochi.lock`.

10. **Symbol name collisions across .NET packages.** Two different NuGet packages exporting methods with the same name produce `[UnmanagedCallersOnly]` symbols like `mochi_dotnet_<pkg>_<Type>_<Method>`. If `<pkg>` is the same (e.g., two different major versions of the same package), collision is possible. Mitigation: the symbol naming scheme includes the package major version: `mochi_dotnet_<id>_v<major>_<Type>_<Method>`.

11. **decimal type precision.** .NET's `decimal` is a 128-bit fixed-point type with no direct equivalent in Mochi or Rust. The bridge maps it to a two-field struct `{ lo: long, hi: long }` at the C ABI boundary and emits a Mochi `decimal` opaque type backed by that struct. Arithmetic on Mochi `decimal` values requires calling back into the .NET wrapper's arithmetic symbols (`mochi_dotnet_decimal_add`, etc.). This is verbose but correct.

12. **Nullable reference type annotations.** C# 8+ nullable reference types (`string?`, `List<T>?`) are advisory annotations in the compiler, not enforced at the IL level; the IL for `string` and `string?` is identical. The ECMA-335 reader detects nullable annotations via the `System.Runtime.CompilerServices.NullableAttribute` custom attribute on parameters and returns, and propagates them to the type table as `T|nil`. Packages compiled without nullable annotations (older or non-annotated packages) have no `Nullable` attribute; all reference-type parameters are translated as non-null with a `SkipReport` warning.
