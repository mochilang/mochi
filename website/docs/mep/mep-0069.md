## Abstract

Mochi today (May 2026, immediately after MEP-53's Swift target landed and MEP-57's source-level package system reached Draft) has ten code-emitting targets including Swift via `transpiler3/swift/`, but only one direction of Swift integration: Mochi source lowered to Swift source compiled by `swift build`. The Mochi-to-Swift path (MEP-53) emits a Swift executable or library that ships the `MochiRuntime` Swift package as its only Swift dependency; user-written Mochi programs cannot pull in arbitrary packages from the Swift Package Manager (SPM) ecosystem, and a Mochi package author cannot publish their work as a Swift package that downstream Swift users `swift package add`. The 300,000+ Swift packages indexed on the Swift Package Index (SPI, April 2026) remain off-limits to Mochi authors, and the Swift ecosystem cannot consume Mochi packages directly.

MEP-69 specifies the **bidirectional Swift Package Manager bridge**: Mochi packages can consume any well-formed Swift package via `import swift "<package>@<semver>" as <alias>` with no user-written FFI boilerplate, and Mochi packages can publish to SPM-compatible destinations (git remotes and SE-0292 registries) as Swift library packages via `mochi pkg publish --to=swift-registry`. The bridge is the sixth source-language interop story Mochi ships (after Go, Python, TypeScript, Rust, and .NET), and the first one targeting an ecosystem whose primary distribution mechanism is git tags rather than a centralised binary registry.

The proposal builds on MEP-57's manifest / lockfile / capability infrastructure and MEP-53's Swift emit pipeline, and adds a new self-contained component under `package3/swift/`. The Mochi grammar gains the single keyword `swift` as a valid `<lang>` token in the existing FFI-import production (no other surface-syntax changes). The Mochi build pipeline gains one new target (`TargetSwiftLibrary` in MEP-53's build driver). The lockfile gains one new repeated table (`[[swift-package]]`). No existing transpiler MEP needs to change.

The system is anchored on seven load-bearing decisions, each justified in §Rationale and surveyed in the companion research notes:

1. **`.swiftinterface` (Swift module interface) files as the canonical machine-readable Swift package surface.** Since Swift 5.1 (SE-0235, stabilised through Swift 5.9+), the Swift compiler can emit textual `.swiftinterface` files alongside compiled module binaries. A `.swiftinterface` file is a compiler-parseable, version-stable serialisation of every public declaration in a Swift module: functions with full type signatures, structs, enums, classes, protocols, typealiases, and generic constraints. The bridge invokes `swiftc -emit-module-interface-path` (or reads pre-built `.swiftinterface` files from a package's `.build/` directory after a `swift build`) and parses the resulting text in a purpose-built Go-side parser (`pkg/pkgswift/swiftinterface/`). Parsing `.swift` source directly is rejected (source-level parsing would require a full Swift grammar implementation in Go and would be defeated by conditional compilation `#if`/`#else`/`#available` blocks and `@_implementationOnly` imports). Using Swift's `swift-syntax` library via a subprocess is rejected for the primary path (it requires a Swift runtime at bind time, coupling the Go host binary to a Swift toolchain version). See [[01-language-surface]] §2, [[04-swiftinterface-ingest]] §1, [[02-design-philosophy]] §1.

2. **Auto-synthesised `@_cdecl`-annotated Swift wrapper package (`swift_wrap/<pkg>/`) per imported Swift dep, not direct `dlopen` or direct Objective-C bridging.** For each Swift package the user imports, the bridge generates a sibling Swift package (`<workdir>/swift_wrap/<pkg>/`) that depends on the source package and exposes a flat C-ABI surface via `@_cdecl`: value types (`struct`, `enum` with associated values) become opaque handles (`UnsafeMutableRawPointer` managed by a `MochiHandle` class that owns the Swift value via an existential box), `String` becomes a `(UnsafePointer<CChar>, Int)` pair plus an explicit `mochi_swift_<pkg>_string_free` symbol, `[T]` becomes a `(UnsafeRawPointer, Int, Int)` triple (ptr/count/stride) plus a `_free` symbol, `Optional<T>` becomes a presence flag plus a value out-pointer, `Result<T, E>` becomes a status code plus two out-pointers, `async` functions are wrapped through a `DispatchGroup`-based synchronous dispatcher that calls into a `Task` (using `Task { ... }` plus `group.wait()`), and `throws` functions translate to `Result`-style error out-pointer pairs. The wrapper package is built as a static library (`TYPE_LIBRARY_STATIC` in SwiftPM) and linked into the final binary by the MEP-53 driver. This indirection accepts the wrapper-codegen cost in exchange for a clean Mochi-side ABI (no need to teach Mochi's lowering pass about Swift generics, protocol witnesses, or existential containers), and a per-wrapper SHA-256 lockfile pin that catches silent `.swiftinterface` drift. See [[02-design-philosophy]] §2, [[03-prior-art-bridges]] §3, [[09-abi-stability]] §1.

3. **Closed Swift-to-Mochi type translation table, with explicit refusal on out-of-table cases.** The translation covers `Int/Int64↔int`, `Int32↔int` (with truncation warning), `Double↔float`, `Float↔float` (with precision note), `String↔string`, `Bool↔bool`, `Void↔unit`, `[T]↔list<T>` (when T is in-table), `[K: V]↔map<K, V>` (when K is String or an integer type and V is in-table), `Set<T>↔set<T>` (when T is Hashable and in-table), `T?↔T|nil` (Optional), `Result<T, E>↔ try-catch desugar`, tuple types `(A, B)↔tuple<A, B>`, fieldful struct types `struct S { var a: A; var b: B }↔record S { a: A; b: B }`, and enum types (C-like `enum E { case v1, v2 }↔type E = v1 | v2` and associated-value `enum E { case v1(A) }↔type E = v1(A)`). Items outside the table (existential `any P` in return position, `some P` opaque return types without a concrete monomorphisation, non-final class types other than as opaque handles, `@escaping` closures without declared arity, `UnsafePointer<T>` and `UnsafeMutablePointer<T>` without `[capabilities] unsafe = true`, Objective-C-only types (`@objc` protocols, `NSObject` subclasses without `@_cdecl`-friendly initialisers), `@_alwaysEmitIntoClient` items that are inlined and have no ABI entry point, and Swift macros) are skipped with a `SkipReport` entry. The user can override with a hand-written `extern fn` declaration. See [[05-type-mapping]] §1, [[02-design-philosophy]] §3.

4. **`import swift "<package>@<semver>" as <alias>` as the sole surface keyword, with `<semver>` resolved through `mochi.lock`.** The grammar gains exactly one new lexeme: the keyword `swift` admitted as a `<lang>` in the existing `import <lang> "<spec>" as <alias>` production. The `<spec>` is `<package-identity>`, `<package-identity>@<semver-req>`, `<package-identity>@git+<url>#<rev>`, `<package-identity>@git+<url>#branch:<branch>`, or `<package-identity>@path+<relative-path>`. Package identity is either a bare package name (resolved through an SE-0292 registry or the mochi.toml `[swift.registries]` table) or a git URL shorthand (e.g., `github.com/Alamofire/Alamofire`). Bare names without a registry declaration resolve through the Swift Package Index API at lock time. The `mochi.lock` lockfile records the resolved version, BLAKE3-256 + SHA-256 of the source archive, the `.swiftinterface` hash, the wrapper SHA-256, and the capability surface. No other Mochi syntax changes are introduced; `import swift` participates in the same module-resolution flow as `import go` / `import python` / `import rust`. See [[01-language-surface]] §1, [[06-spm-publish-flow]] §2.

5. **Mochi → Swift package emission via a new `TargetSwiftLibrary` MEP-53 target.** MEP-53 today exposes Swift as a transpilation target (`TargetSwiftSource`, `TargetSwiftExecutable`). MEP-69 adds `TargetSwiftLibrary`. The library path emits a complete Swift package directory: a `Package.swift` manifest declaring the package identity, Swift tools version, supported platforms, products (`.library(name:targets:)`), and the `MochiRuntime` dependency; one Swift source file per Mochi module (`Sources/<module>/<module>.swift`) with `public func`, `public struct`, and `public enum` items mirroring the Mochi package's public surface; a `Sources/<module>/MochiBridge.swift` file exporting the C ABI surface for downstream non-Swift consumers via `@_cdecl` and `@_expose(Cxx)`; and a `README.md` generated from the Mochi package's doc comments. The `[swift.publish]` section of `mochi.toml` populates the package identity, version, supported platforms, and SE-0292 metadata. See [[01-language-surface]] §3, [[07-spm-publish-flow]] §1.

6. **Dual publish path: git-tag push (classical SPM) plus SE-0292 registry API (structured registry).** The SPM ecosystem since Swift 5.5 has used git tags as its canonical version mechanism: `swift package add https://github.com/Alamofire/Alamofire.git --from 5.9.1` resolves the package at the `5.9.1` tag on the git remote. MEP-69 supports this classical path as the default: `mochi pkg publish --to=swift-git` pushes a semver-compliant git tag to the configured remote after building the library. The structured alternative (`--to=swift-registry`) uses the SE-0292 registry API, which Apple adopted in Swift 5.7 (2022) and which Swift Package Index operates as a pilot for; this path POSTs the source archive plus package manifest to an SE-0292 endpoint and records a corresponding signed release. Both paths sign the release using Sigstore-keyless OIDC where supported; the git-tag path falls back to a git-signed tag (GPG or SSH via `commit.gpgsign`). Long-lived registry API tokens are not required or accepted for the structured path; the SE-0292 token exchange uses the GitHub Actions OIDC flow. See [[07-spm-publish-flow]] §1, [[02-design-philosophy]] §5.

7. **Swift Concurrency bridge via synchronous `DispatchGroup`-bounded `Task` dispatch for `async` functions, with opt-in `async` colour propagation for high-throughput use cases.** Swift's structured concurrency (`async`/`await`, introduced Swift 5.5, SE-0296) is deeply integrated into the Apple platform SDK and many modern Swift packages (swift-nio, Vapor, Alamofire 6.x). Mochi's source-level `async` is colouring-only and lowers to immediate evaluation on the same thread in the MEP-53 Swift target. The bridge resolves the impedance mismatch at the wrapper level: each `async func` in the imported package is wrapped via a generated Swift stub that fires a `Task { ... }` and immediately blocks on a `DispatchGroup` (`group.enter(); Task { defer { group.leave() }; result = try? await ...; }; group.wait()`). This pattern is safe in the Mochi call context (the calling thread has no Swift Concurrency executor attached) and is the same synchronous-dispatch strategy used by swift-bridge and UniFFI's Swift backend. Users who need non-blocking async propagation can opt in via `[swift.runtime] async-mode = "actor"`, which surfaces the async function as a Mochi `async fun` that dispatches through the Swift global concurrency executor and returns a future. See [[08-async-bridge]] §1, [[02-design-philosophy]] §4.

The gate for each delivery phase is empirical: the bridge must successfully ingest a curated 20-package fixture corpus (drawn from the Swift Package Index April 2026 most-downloaded snapshot: Alamofire, swift-argument-parser, swift-log, swift-crypto, swift-collections, swift-nio, swift-http-types, SwiftyJSON, RxSwift, Vapor, Leaf, GRDB, SQLite.swift, KeychainAccess, SwiftProtobuf, CombineExt, Defaults, Files, Rainbow, Ink); generate a translatable surface for every public item the closed type-table covers; emit a `SkipReport` for every item out of table; produce a Mochi `extern fn` corpus that parses cleanly; and build the resulting wrapper-plus-Mochi binary via MEP-53's existing `swift build --configuration release` path with zero additional flags. A separate publish gate exercises the `TargetSwiftLibrary` path against a local SE-0292 registry harness, asserts that the published package resolves cleanly via `swift package add`, and asserts that the git-tag publish path produces a tag that a bare `swift package` dependency declaration can consume.

## Motivation

Mochi today (May 2026) integrates with five foreign ecosystems: Go, Python, TypeScript, Rust, and .NET. Each integration covers a different technical niche; Swift covers two niches none of the others reach:

1. **The Swift ecosystem is the canonical 2024-2026 destination for Apple platform development and a rapidly-growing destination for server-side work.** The Swift Package Index indexes 300,000+ packages (April 2026). UIKit and AppKit are Swift-first, SwiftUI is Swift-only, and all modern Apple SDK APIs since iOS 16 / macOS 13 have Swift-native async signatures. A Mochi program targeting an iOS or macOS app cannot access the App Store, push notifications, Core Data, AVFoundation, or Core ML without Swift interop. Server-side Swift (Vapor, Hummingbird, swift-aws-lambda-runtime) is the fastest-growing part of the ecosystem; a Mochi backend author targeting AWS Lambda on Swift has no path to the swift-aws-lambda-runtime SDK today.

2. **The Swift ecosystem expects Swift packages as the unit of distribution.** When a Mochi package author writes a library useful to iOS or macOS developers, the distribution channel is `swift package add` or an Xcode package dependency declaration. MEP-53's Swift transpiler emits Swift source but does not generate a `Package.swift` with the right product, target, and platform declarations; MEP-69 adds `TargetSwiftLibrary` to fill this gap, producing a package any Swift developer can add with one line.

3. **Swift packages are the only major ecosystem where git tags, not a binary registry, are the canonical version-pinning mechanism.** SPM resolved packages via git tags from its introduction (Swift 3.0, 2016) through to the present. The SE-0292 registry API (2022) adds a structured path but does not replace the git-tag model; both coexist. Mochi's existing `mochi pkg publish` infrastructure (MEP-57) is built around signing-and-uploading a content tarball; the git-tag path is architecturally different and requires teaching the publish flow about git operations. MEP-69 is the first Mochi bridge to ship both a tarball-upload publish path and a git-tag push path.

4. **Swift's `.swiftinterface` module interface format provides a stable, compiler-parseable, version-tolerant machine-readable API surface.** Prior to SE-0235 (Swift 5.1, 2019), the only way to inspect a Swift module's public surface was to run the compiler on source or to parse binary `.swiftmodule` files (which are not stable across compiler versions). `.swiftinterface` files are textual, human-readable, and stable across compiler versions within a major Swift release. Apple ships `.swiftinterface` files for every Apple SDK framework, making the same ingest path work for SDK types (when the user has an explicit Apple platform target). The analogy to MEP-73's rustdoc JSON approach is exact; the bridge reads `.swiftinterface` and treats it as authoritative.

5. **The `import swift` surface has zero learning curve for Mochi users.** `import swift "github.com/vapor/vapor@^4.99" as vapor` is the same shape as `import rust "tokio@^1.42" as tokio` and `import go "strings"`. Mochi users do not need to know what a `Package.swift` is, what a `@_cdecl` annotation is, what an existential container is, what a Swift actor is, what a `Task` is, what a module interface file is, or what SE-0292 is. They write `import swift "..." as ...` and the bridge does the rest.

6. **MEP-57 already shipped the prerequisite manifest / lockfile / capability infrastructure.** The `mochi.toml` table layout, the `mochi.lock` serialisation, the BLAKE3-256 + SHA-256 dual-hashing, the trusted-publishing OIDC token exchange, and the capability declaration model all transfer to the Swift bridge. MEP-69 is additive on top of MEP-57: one new manifest section (`[swift-dependencies]`), one new lockfile repeated table (`[[swift-package]]`), one new CLI surface (`mochi pkg publish --to=swift-registry` and `mochi pkg publish --to=swift-git`).

7. **The bridge stays small and audit-friendly.** The reference implementation under `package3/swift/` is targeted at approximately 7,000 LOC of Go across the SPM git resolver, the SE-0292 registry client, the `.swiftinterface` parser, the type-mapping pass, the `@_cdecl` wrapper synthesiser, the Mochi extern emitter, the lockfile integrator, the publish flows, and the Swift Concurrency bridge hook. There is no Swift-side dynamic codegen at user-machine time (the wrapper is fully synthesised by the Go binary; the user's `swift build` only compiles, never generates code from `.swiftinterface`). There are no Swift macros in the synthesised wrapper (they would defeat reproducibility). There is no `withUnsafePointer` in the synthesised wrapper unless the user opts in via `[swift.capabilities] unsafe = true`.

## Specification

This section is normative. Sub-notes under [/docs/research/0069/](/docs/research/0069/) are informative.

### 1. Pipeline overview

MEP-69 introduces a per-import Swift dependency resolution layer that sits between the Mochi parser (after MEP-57 has resolved `mochi.toml`) and the MEP-53 build driver:

```
mochi.toml [swift-dependencies]
   |  pkgmanifest.Parse + pkgsolver.Solve (MEP-57)
   v
resolved Swift dep tree (package identity + version + source URL)
   |  package3/swift/spmresolver.Fetch (SPM git clone or SE-0292 registry pull)
   v
Swift source archives in ~/.cache/mochi/swift-deps/<blake3-hex>/
   |  package3/swift/swiftinterface.Generate (swiftc -emit-module-interface)
   v
.swiftinterface document per module per package
   |  package3/swift/typemap.Translate (closed Swift-to-Mochi table)
   v
TranslatedSurface + SkipReport per package
   |  package3/swift/wrapsyn.Emit (synthesised @_cdecl wrapper package)
   v
swift_wrap/<pkg>/ SwiftPM package member
   |  package3/swift/externemit.Emit (Mochi extern fn / extern type)
   v
synthesised .mochi shim file per package, imported by the user's source
   |  MEP-53 Driver.Build (TargetSwiftExecutable / TargetSwiftLibrary)
   v
binary or Swift package
```

The bridge does not run the Swift compiler at ingest time beyond `swift package dump-package` (JSON manifest extraction) and `swift build --show-bin-path` (locating pre-built `.swiftinterface` files). The wrapper package is emitted as Swift source by the Go side and compiled by the user's normal `swift build --configuration release` (orchestrated by the MEP-53 driver) alongside the user's program.

### 2. Manifest extension: `[swift-dependencies]` and `[swift]`

The MEP-57 `mochi.toml` gains two new optional top-level tables:

```toml
[swift-dependencies]
Alamofire = { version = "^5.9", url = "https://github.com/Alamofire/Alamofire.git" }
"swift-argument-parser" = { version = "^1.5", url = "https://github.com/apple/swift-argument-parser.git" }
"swift-nio" = { version = "^2.75", url = "https://github.com/apple/swift-nio.git" }
Vapor = { version = "^4.99", url = "https://github.com/vapor/vapor.git" }
MyLocalPackage = { path = "../MySwiftPackage" }

[swift]
tools-version = "5.9"
platforms = [
    { name = "macOS", version = "13.0" },
    { name = "iOS", version = "16.0" },
]
runtime = { async-mode = "dispatch-group" }
monomorphise = [
    { item = "swift-collections.OrderedDictionary", K = "String", V = "Int" },
]

[swift.registries]
default = "https://packages.swift.org"
myorg = "https://registry.mycompany.com/swift"

[swift.publish]
package-name = "MyMochiLib"
github-repo = "github.com/myorg/MyMochiLib"
platforms = [
    { name = "macOS", version = "13.0" },
    { name = "iOS", version = "16.0" },
    { name = "linux", version = "" },
]
registry = "https://packages.swift.org"

[swift.capabilities]
net = true
fs = false
proc = false
objc = false
unsafe = false
```

`[swift-dependencies]` follows SPM's package dependency grammar:

- `url`: the git remote URL. Required unless `path` is set or the package name is resolvable via an SE-0292 registry.
- `version`: a semver range constraint (`^5.9`, `>=5.9.0, <6.0.0`, `exact: 5.9.1`). Maps to SPM's `.upToNextMajor(from:)`, `.upToNextMinor(from:)`, and `.exact()` dependency requirements.
- `branch`: a git branch name. Mutually exclusive with `version`.
- `revision`: a git commit SHA. Mutually exclusive with `version` and `branch`.
- `path`: a local filesystem path. Mutually exclusive with all remote fields.

The user can omit `url` if a matching package is registered in the configured `[swift.registries]` tables; the bridge queries the registry for the canonical source URL at lock time.

The `[swift]` table holds Mochi-specific knobs:

- `tools-version`: the Swift tools version for the synthesised `Package.swift`. Default `"5.9"` (stable since Xcode 15 / Swift 5.9, September 2023).
- `platforms`: a list of `{ name, version }` pairs. Maps to the `platforms:` argument in `Package.swift`. Default `[{ name: "macOS", version: "13.0" }]`. Add `{ name: "linux", version: "" }` to enable Linux (no version requirement).
- `runtime.async-mode`: `"dispatch-group"` (default) or `"actor"`. Controls how `async func` items in imported packages are exposed to Mochi.
- `monomorphise`: a list of explicit generic instantiations for the type-mapping pass.

The `[swift.registries]` table maps registry names to SE-0292 base URLs. `default` is the registry queried when a package name has no explicit `url` and no other named registry applies.

The `[swift.publish]` table holds Mochi-as-library knobs:

- `package-name`: the Swift package identity name. Defaults to the `mochi.toml` `[package].name` field.
- `github-repo`: the GitHub/GitLab/Gitea remote (`owner/repo` or full URL) for the git-tag publish path.
- `platforms`: the `platforms:` array in the emitted `Package.swift`.
- `registry`: the SE-0292 registry endpoint for the `--to=swift-registry` publish path.

The `[swift.capabilities]` table holds Swift-bridge-specific capability flags:

- `net`: the package graph contains packages that open network connections (Alamofire, swift-nio, Vapor). Default `false`.
- `fs`: the package graph reads or writes files. Default `false`.
- `proc`: the package graph spawns subprocesses. Default `false`.
- `objc`: the package graph contains Objective-C-bridged types (`@objc` protocols, `NSObject` subclasses). Default `false`. Enabling this requires an Apple platform target.
- `unsafe`: the package graph contains `withUnsafePointer` / `withUnsafeMutableBytes` items that the user has hand-overridden. Default `false`.

### 3. Lockfile extension: `[[swift-package]]`

The MEP-57 `mochi.lock` gains one new repeated table:

```toml
[[swift-package]]
name = "Alamofire"
version = "5.9.1"
source = { kind = "git", url = "https://github.com/Alamofire/Alamofire.git", ref = "5.9.1", commit = "abc1234..." }
archive-blake3 = "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
archive-sha256 = "fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210"
swiftinterface-sha256 = "..."
wrapper-sha256 = "..."
swift-tools-version = "5.9"
capabilities-declared = ["net"]
dependencies = ["swift-log@^1.5", "swift-http-types@^1.3"]
```

`archive-blake3` and `archive-sha256` are the integrity hashes of the source archive: the git-exported tarball at the pinned commit SHA. BLAKE3-256 is the primary verification hash (matches MEP-57's broader BLAKE3 + SHA-256 dual-hashing rule). SHA-256 is recorded for cross-ecosystem interoperability and for future SE-0292 registry cross-check (SE-0292 registries record SHA-256 of release archives).

`swiftinterface-sha256` records the SHA-256 of the composite `.swiftinterface` document (all modules in the package concatenated in deterministic order) the bridge ingested at lock time. A drift here at `mochi pkg lock --check` time is a hard error.

`wrapper-sha256` records the SHA-256 of the synthesised wrapper package's primary source file. A drift at `--check` time is a hard error.

`swift-tools-version` records the `// swift-tools-version:` header the package's `Package.swift` declared. A tools-version change between lock runs is a hard error pending explicit re-lock.

`capabilities-declared` is the capability set the manifest declared at lock time. A capability addition at `--check` time is a hard error pending re-acknowledgement (MEP-57 §1.6 monotonicity rule).

`dependencies` is the resolved transitive dependency list (immediate upstream packages the SPM resolver walked when constructing the dep graph).

### 4. Surface syntax: `import swift "..."`

The Mochi grammar's existing FFI-import production:

```
ImportStmt := "import" Lang? StringLit "as" Ident ("auto")?
Lang := "go" | "python" | "typescript" | "rust" | "dotnet" | "swift"
```

gains `swift` as a `Lang` alternative. The string literal is one of:

| Form | Resolution |
|------|------------|
| `<package-name>` | Bare name. Resolves through `[swift.registries]` or the Swift Package Index API. |
| `<package-name>@<semver-req>` | Explicit version constraint. Must match `[swift-dependencies]`. |
| `<owner>/<repo>@<semver-req>` | GitHub/GitLab shorthand. Expands to `https://github.com/<owner>/<repo>.git`. |
| `github.com/<owner>/<repo>@<semver-req>` | Fully qualified git shorthand. |
| `<package-name>@git+<url>#<rev>` | Pinned git revision or tag. |
| `<package-name>@git+<url>#branch:<branch>` | Git branch. |
| `<package-name>@path+<rel-path>` | Local path. |

Example surface programs:

```mochi
import swift "Alamofire@^5.9" as http
import swift "vapor/vapor@^4.99" as vapor
import swift "swift-argument-parser" as args
import swift "swift-collections@^1.1" as collections

fn fetch_user(id: string): string {
    let response = http.AF.request("https://api.example.com/users/\(id)").response()
    return response.data?.utf8String ?? ""
}

fn parse_args(): Args {
    return args.ArgumentParser.parseOrExit(Args.self)
}
```

The `<alias>` introduces a Mochi namespace; symbol resolution looks up `<alias>.<item>` and binds against the synthesised `extern fn` declaration the bridge generated for the Swift module's `<item>`. Swift module names (PascalCase by convention) are preserved in the shim; the user accesses them as `alias.ModuleName.functionName` or, with the `auto` modifier, directly as `functionName`.

The `auto` keyword (accepted for `import go ... auto` and `import rust ... auto`) is admitted for `import swift ... auto` to opt into flat namespace binding.

### 5. CLI surface

The Mochi CLI gains the following additions, all under the existing `mochi pkg` subcommand:

- `mochi pkg add swift <package>[@<semver>] [--url=<git-url>]`: adds an entry to `[swift-dependencies]` and runs `mochi pkg lock`.
- `mochi pkg lock`: extended to walk `[swift-dependencies]`, resolve each package (via git or SE-0292 registry), clone/fetch the source into the content-addressed cache, build `.swiftinterface` files, synthesise the wrapper, and write `[[swift-package]]` entries.
- `mochi pkg lock --check`: extended to verify `archive-blake3`, `swiftinterface-sha256`, `wrapper-sha256`, and `capabilities-declared` for every `[[swift-package]]` entry.
- `mochi pkg lock --accept-capability=<cap>`: re-locks after explicitly acknowledging a capability addition detected by `--check`.
- `mochi pkg publish --to=swift-git [--remote=<url>] [--dry-run]`: builds the package via `TargetSwiftLibrary`, pushes a semver git tag to the configured remote. `--dry-run` creates the tag locally without pushing.
- `mochi pkg publish --to=swift-registry [--registry=<url>] [--dry-run]`: builds the package, packages it as a source archive, POSTs it to the configured SE-0292 registry endpoint with an OIDC token. `--dry-run` validates the manifest without uploading.
- `mochi pkg publish --to=swift-registry --emit-ci`: generates a `.github/workflows/release.yml` workflow for automated git-tag + registry publish on version tags.
- `mochi pkg sync swift`: regenerates the wrapper from the existing `mochi.lock` without re-resolving. Used after manual edits to the synthesised shim or after a bridge upgrade.

### 6. Build orchestration

When a Mochi program contains one or more `import swift "..."` declarations, the MEP-53 build driver gains the following extensions:

1. Before invoking `swift build`, the driver invokes `package3/swift/Bridge.PrepareWorkspace(workdir, mochiLock)` which:
   - For each `[[swift-package]]` in `mochi.lock`, materialises the package source from the content-addressed cache into `<workdir>/swift_deps/<pkg>-<version>/`.
   - Materialises the synthesised wrapper package into `<workdir>/swift_wrap/<pkg>/`.
   - Writes a `<workdir>/Package.swift` workspace manifest that includes the main package, every `<workdir>/swift_wrap/<pkg>/` as a local package dependency, and the `MochiRuntime` package (from `transpiler3/swift/runtime/`).
   - Each wrapper package's `Package.swift` declares the source package as a local dependency pointing to `<workdir>/swift_deps/<pkg>-<version>/`.

2. The MEP-53 emit pass treats each `import swift "<pkg>" as <alias>` as a Mochi `import "./swift_wrap/<pkg>/shim.mochi" as <alias>` shim, where the shim file is the `extern fn` corpus the bridge emitted.

3. The user's `swift build --configuration release` (invoked by `Driver.Build`) compiles every package in the workspace, producing the wrapper as a static archive, and links the main binary against it via `-lswift_wrap_<pkg>`.

4. The driver invalidates the cache when any `[[swift-package]]` `wrapper-sha256` changes (per MEP-53 phase 0's cache-key construction).

5. For Apple platform targets (macOS, iOS), the driver produces an XCFramework bundle when `[swift] xcframework = true` is set in `mochi.toml`. The XCFramework bundles the compiled `.swiftmodule`, `.swiftinterface`, and static archive for each supported SDK target (macOS-arm64, macOS-x86_64, iOS-arm64, iOS-simulator-arm64, iOS-simulator-x86_64) into a single `.xcframework` directory.

### 7. Async bridge runtime hook

The wrapper package for any source package that exposes `async func` items includes a generated `MochiAsync.swift` module:

```swift
import Foundation

func mochiRunAsync<T>(_ body: @escaping () async throws -> T) -> Result<T, Error> {
    var result: Result<T, Error>!
    let group = DispatchGroup()
    group.enter()
    Task {
        defer { group.leave() }
        do {
            result = .success(try await body())
        } catch {
            result = .failure(error)
        }
    }
    group.wait()
    return result
}
```

The wrapper for `async func fetch(_ url: String) async throws -> Data` becomes:

```swift
@_cdecl("mochi_Alamofire_fetch")
public func mochi_Alamofire_fetch(_ url_ptr: UnsafePointer<CChar>, _ url_len: Int,
                                   _ out_data: UnsafeMutablePointer<UnsafeMutableRawPointer?>,
                                   _ out_len: UnsafeMutablePointer<Int>) -> Int32 {
    let url = String(bytes: UnsafeBufferPointer(start: url_ptr, count: url_len), encoding: .utf8)!
    let res = mochiRunAsync { try await SomePackage.fetch(url) }
    switch res {
    case .success(let data):
        let ptr = UnsafeMutableRawPointer.allocate(byteCount: data.count, alignment: 1)
        data.copyBytes(to: ptr.assumingMemoryBound(to: UInt8.self), count: data.count)
        out_data.pointee = ptr
        out_len.pointee = data.count
        return 0
    case .failure:
        return 1
    }
}
```

When `[swift.runtime] async-mode = "actor"` is set in `mochi.toml`, `mochiRunAsync` is replaced by a Swift actor-based dispatcher that returns a Mochi `async fun` future instead of blocking.

The `DispatchGroup`-based path is opt-out only (it is the default); programs that never call an `async` Swift function pay zero `DispatchGroup` overhead.

### 8. XCFramework bundle for Apple platform targets

When `[swift] xcframework = true` is set and the build target includes one or more Apple platform entries, the driver runs `xcodebuild -create-xcframework` after the per-sdk static library builds to produce a distributable XCFramework. The XCFramework bundles:

- `macos-arm64_x86_64/`: fat static archive + `.swiftmodule` + `.swiftinterface`
- `ios-arm64/`: iOS device slice
- `ios-arm64_x86_64-simulator/`: iOS simulator fat slice
- `linux-x86_64/`: (included when `platforms` contains `linux`)

The XCFramework is placed at `<outdir>/<package-name>.xcframework/` and is the artefact published by `mochi pkg publish --to=swift-git` when a GitHub release is created.

## Alternatives considered

1. **Parse Swift source directly instead of via `.swiftinterface`.** Rejected: a Swift grammar parser implemented in Go would be a substantial undertaking; conditional compilation blocks (`#if canImport(UIKit)`, `#if os(Linux)`) and `@_implementationOnly` imports mean the source-level surface differs from the compiled surface; Swift macros (SE-0382, Swift 5.9) expand at compile time and are not visible at source level. The bridge takes `.swiftinterface` as authoritative.

2. **Use swift-syntax (Apple's Swift syntax library) as the bind source.** Rejected: `swift-syntax` parses source, not the compiled module interface; the same `#if` conditional compilation problems apply. It would also require a Swift runtime on the bind host, coupling the Go host binary to a specific Swift toolchain version. `.swiftinterface` is compiler-generated and stable across toolchain versions within a major Swift release.

3. **Use SourceKit-LSP's index data as the bind source.** Rejected: SourceKit-LSP is designed for interactive editor use; it does not emit a stable, file-format-versioned JSON document analogous to rustdoc JSON or assembly metadata. Running SourceKit-LSP at lock time would add a 5-10 second startup cost per package and produce output whose schema is not guaranteed stable across Xcode releases.

4. **Use swift-bridge for the FFI layer.** Rejected: `swift-bridge` requires hand-written `#[swift_bridge::bridge]` Rust annotations that generate both Rust and Swift glue code. It violates the "no boilerplate" promise (the user must write a bridge definition for every function they want to call). `swift-bridge` is the right tool when the author wants explicit control; MEP-69 synthesises the bridge from `.swiftinterface`.

5. **Use UniFFI (Mozilla) for the binding layer.** Rejected: UniFFI generates bindings from a UDL interface description file that the library author writes. A Mochi user importing `Alamofire` would have to author a UDL for the entire Alamofire surface, which is more boilerplate than the bridge promise allows. UniFFI is excellent when the binding author controls both sides; MEP-69 generates bindings from the existing `.swiftinterface`.

6. **Use Objective-C interop as the primary bridge (via Swift's `@objc` mechanism).** Rejected: many modern Swift packages (swift-nio, swift-collections, swift-http-types, swift-argument-parser) have no `@objc` surface. The `@objc` mechanism requires classes (reference types), making it unsuitable for value-type-heavy Swift code. `@_cdecl` covers both value types and reference types through the opaque-handle pattern and is not gated on Objective-C runtime availability (works on Linux).

7. **Use cxx (the Rust-C++ bridge library) as inspiration for a Rust-Swift bridge.** Rejected: the Mochi bridge does not go through Rust; it goes directly from Mochi (via the MEP-53 Swift transpiler) to Swift. A Rust-Swift intermediary would add a second wrapper stage and double the compile overhead.

8. **Use WIT (WebAssembly Interface Types) as the bridge protocol.** Rejected for v1: the Swift Wasm Component Model support (via `swift-wasm`) is experimental and does not cover the Apple platform SDK. MEP-69 targets native Swift packages; the WIT path is deferred to a potential v2 that targets swift-wasm component consumers.

9. **Require the user to annotate their Swift package with `@_cdecl` declarations before importing.** Rejected: this is the UniFFI / swift-bridge approach and violates the "no boilerplate" promise. The bridge generates `@_cdecl` exports in the synthesised wrapper; the source package is unmodified.

10. **Use `dlopen` of pre-built Swift `.dylib` artefacts instead of per-import wrapper compilation.** Rejected: pre-built Swift `.dylib` files are platform, architecture, and Swift-ABI-version specific. Swift's ABI is stable on Apple platforms (since Swift 5.0, macOS 10.14.4, iOS 12.2) but not on Linux (each Swift release ships its own stdlib). Downloading pre-built binaries from a package registry requires a binary distribution protocol that SPM does not standardise. The source-compile-and-link path is universal.

11. **Use the Swift `@_expose(Cxx)` attribute instead of `@_cdecl`.** Rejected for the primary path: `@_expose(Cxx)` is a C++ interop feature (SE-0297, Swift 5.9) that generates C++ headers, not C ABI. The Mochi wrapper stack uses the existing C sidecar pattern (MEP-45) which expects C ABI, not C++. `@_expose(Cxx)` is noted as a future optimisation for the XCFramework path where C++ headers are already emitted.

12. **Support long-lived SE-0292 registry API tokens.** Rejected: matches MEP-57's principle that long-lived tokens are deprecated. The SE-0292 registry publish path uses GitHub Actions OIDC where available; the git-tag path is signed with the user's git signing key (GPG or SSH). No static registry token is accepted or stored.

## Risks

1. **`.swiftinterface` stability.** `.swiftinterface` files are versioned by Swift tools version (`// swift-tools-version: 5.9`) but their internal textual format has evolved in each major Swift release. The bridge pins a supported Swift tools version at lock time; an ingest against a newer Swift version that changed the `.swiftinterface` grammar produces a schema-mismatch error. Mitigation: ship a version-compatibility parser that handles the `5.5` through `6.0` grammar variations; update the parser when a new major Swift release ships.

2. **Linux Swift ABI instability.** Swift on Linux does not have a stable ABI across major releases (unlike Apple platforms where Swift ABI has been stable since 5.0). A Mochi binary linked against a wrapper compiled with Swift 5.10 cannot be combined with one compiled with Swift 6.0 on Linux. Mitigation: the bridge enforces that all packages in `mochi.lock` were compiled with the same Swift toolchain version (per the `swift-tools-version` field); a toolchain upgrade forces a full re-lock and re-wrapper.

3. **Wrapper package compile times.** A wrapper for Alamofire covers approximately 200 public symbols; `swift build` takes ~12 seconds warm, ~35 seconds cold on an Apple M2. For a Mochi program with 5 Swift package imports, the wrapper compile pass adds ~60 seconds to the cold build time. Mitigation: wrapper static archives are cached in `~/.cache/mochi/swift-deps/wrappers/<wrapper-sha256>/`; subsequent builds with the same wrapper SHA-256 are cache hits.

4. **SPM git resolution is slow for packages with large histories.** A shallow clone (`--depth=1`) at the pinned tag reduces the git fetch cost; the bridge uses shallow clones by default and escalates to full clones only when a `revision:` (not a semver tag) is specified.

5. **Apple-platform-only packages.** Many of the most popular Swift packages (SwiftUI views, UIKit extensions, Core Data wrappers) contain Apple-SDK-specific types that fail to compile on Linux. The bridge detects `#if canImport(UIKit)` / `#if os(macOS)` guards in the `Package.swift` platform declarations and marks the package `apple-only = true` in the lockfile; attempting to build it on Linux produces a clear diagnostic. Mitigation: the fixture corpus is split into cross-platform packages (phases 0-16) and Apple-only packages (phase 17 Objective-C subset).

6. **SE-0292 registry GA fragmentation.** The SE-0292 registry protocol is specified and implemented in Swift Package Manager but not universally adopted; most packages are still consumed via git URLs. The Swift Package Index registry pilot is limited to indexed packages. Mitigation: the bridge defaults to the git-tag publish path; SE-0292 registry publish is opt-in via `--to=swift-registry`.

7. **Generic Swift APIs.** Swift's generics are more expressive than Mochi's type system can represent (associated types, `some` opaque return types, existential `any P` in return position). The type-mapping table refuses these items with `SkipReport`; the user must enumerate explicit monomorphisations in `[swift.monomorphise]` to import a generic function. Mitigation: the fixture corpus includes several generic-heavy packages (swift-collections, swift-algorithms) to validate the monomorphisation path.

8. **Swift Concurrency actor isolation.** Some modern Swift packages mark types as `@MainActor` or use custom actor isolation. The `@_cdecl` wrapper cannot be called from an actor context (it has no `@Sendable` annotation). Calls to `@MainActor`-isolated functions from the `DispatchGroup`-bounded `Task { }` wrapper may dead-lock if the main thread is blocked. Mitigation: the bridge emits a `SkipReport` for any function annotated `@MainActor` unless the user opts in via `[swift.capabilities] main-actor = true`; the opt-in wrapper uses a `Task.detached` instead of `Task { }` to avoid executor contention.

9. **Swift macros are not in the ABI surface.** Swift macros (SE-0382, Swift 5.9) are compile-time code generators that expand into Swift source; they do not appear as callable items in `.swiftinterface` files. A Swift package that offers its primary user-facing API entirely through macros (e.g., `@Observable`, `@Codable`) cannot be wrapped by the bridge. Mitigation: the `SkipReport` documents macro-only items; the user must use the underlying non-macro API or write a hand-authored Swift wrapper.

10. **XCFramework binary size.** An XCFramework bundling the static archive for five sdk-architectures (macOS-fat, iOS-arm64, iOS-simulator-fat, plus the wrapper code) can reach 20+ MB for packages with large symbol counts. Mitigation: `swift build` with `-Osize` reduces binary size; the bridge applies `-Osize` for XCFramework builds by default.

11. **Git-tag publish and tag drift.** A git-tag push can be overwritten (`git tag -f`) by anyone with push access to the remote, undermining reproducibility. Mitigation: the bridge emits a warning when `mochi pkg lock --check` finds that the resolved commit for a tag in `mochi.lock` no longer matches the live tag on the remote; the user must explicitly re-lock to accept the new commit.

12. **Linux package restoration and Swift stdlib size.** Swift on Linux requires distributing the Swift standard library (approximately 50 MB of `.so` files) alongside the binary unless the binary is statically linked. The bridge defaults to a static-stdlib Linux build (`swiftc -static-stdlib`) for command-line tool targets; library targets link dynamically and document the stdlib dependency.
