# 11. XCFramework and multi-platform

## What an XCFramework is

An XCFramework (introduced in Xcode 11, 2019) is a directory bundle (`.xcframework`) that aggregates multiple platform/architecture slices of a binary framework into a single distributable artefact. Xcode and SwiftPM's binary target feature automatically select the correct slice for the build target.

Structure:

```
MyMochiLib.xcframework/
  Info.plist                        # Manifest: lists all slices and their library paths
  macos-arm64_x86_64/               # macOS fat binary slice
    MyMochiLib.framework/
      MyMochiLib                    # fat Mach-O static archive (arm64 + x86_64)
      Headers/
        MyMochiLib.h                # Generated C header (from @_cdecl exports)
      Modules/
        MyMochiLib.swiftmodule/
          arm64-apple-macos.swiftinterface
          x86_64-apple-macos.swiftinterface
  ios-arm64/                        # iOS device slice
    MyMochiLib.framework/
      MyMochiLib                    # arm64 static archive
      ...
  ios-arm64_x86_64-simulator/       # iOS simulator fat binary (arm64 + x86_64)
    MyMochiLib.framework/
      MyMochiLib                    # fat Mach-O static archive
      ...
  linux-x86_64/                     # Linux slice (when platforms includes linux)
    libMyMochiLib.a                 # ar static archive (no framework wrapper)
    MyMochiLib.swiftmodule/
      x86_64-unknown-linux-gnu.swiftinterface
```

## When XCFramework is produced

XCFramework production is opt-in via `[swift] xcframework = true` in `mochi.toml`. It is produced when:

1. The build target includes at least one Apple platform entry (`macOS`, `iOS`, etc.) in `[swift] platforms`.
2. The Mochi build host is a macOS system with Xcode installed (XCFramework production requires `xcodebuild` and the Apple SDK, which are only available on macOS).

For Linux-only builds (server-side Swift, CI without Xcode), XCFramework is not produced; the build outputs a single static archive.

## Build pipeline for XCFramework production

When `xcframework = true`:

1. **Compile per SDK.** The MEP-53 build driver invokes `swift build --configuration release` once per SDK target:
   - `--sdk $(xcrun --sdk macosx --show-sdk-path)` for macOS.
   - `--sdk $(xcrun --sdk iphoneos --show-sdk-path)` for iOS device.
   - `--sdk $(xcrun --sdk iphonesimulator --show-sdk-path)` for iOS simulator.
   - `--swift-sdk <linux-sdk-identifier>` for Linux (requires the Swift SDK for Linux to be installed via `swiftly` or `swift-sdk install`).

2. **Produce fat binaries.** For Apple slices with multiple architectures (macOS: arm64 + x86_64; iOS simulator: arm64 + x86_64), the driver runs `lipo -create` to merge the per-arch static archives into a fat binary.

3. **Bundle the XCFramework.** Runs `xcodebuild -create-xcframework` with a `-library <path> -headers <dir>` argument for each SDK slice:

```bash
xcodebuild -create-xcframework \
  -library .build/arm64-apple-macosx/release/libMyMochiLib.a \
    -headers .build/arm64-apple-macosx/release/include/ \
  -library .build/arm64-apple-ios/release/libMyMochiLib.a \
    -headers .build/arm64-apple-ios/release/include/ \
  -library .build/arm64-apple-ios-simulator/release/libMyMochiLib.a \
    -headers .build/arm64-apple-ios-simulator/release/include/ \
  -output MyMochiLib.xcframework
```

4. **Zip for distribution.** Creates `MyMochiLib.xcframework.zip` (SwiftPM binary targets require a `.zip` archive). Computes SHA-256 of the zip.

5. **Embed in `Package.swift`.** Updates the `Package.swift` to use a `binaryTarget` pointing to the GitHub Release download URL and the SHA-256 checksum. This is done after the zip is uploaded to a GitHub Release (or another CDN).

## `Info.plist` manifest

The XCFramework `Info.plist` is generated by `xcodebuild -create-xcframework` and lists every slice:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<plist version="1.0">
<dict>
    <key>AvailableLibraries</key>
    <array>
        <dict>
            <key>LibraryIdentifier</key><string>macos-arm64_x86_64</string>
            <key>LibraryPath</key><string>MyMochiLib.framework</string>
            <key>SupportedArchitectures</key><array><string>arm64</string><string>x86_64</string></array>
            <key>SupportedPlatform</key><string>macos</string>
        </dict>
        <dict>
            <key>LibraryIdentifier</key><string>ios-arm64</string>
            <key>LibraryPath</key><string>MyMochiLib.framework</string>
            <key>SupportedArchitectures</key><array><string>arm64</string></array>
            <key>SupportedPlatform</key><string>ios</string>
        </dict>
        ...
    </array>
    <key>CFBundlePackageType</key><string>XFWK</string>
    <key>XCFrameworkFormatVersion</key><string>1.0</string>
</dict>
</plist>
```

SwiftPM and Xcode read this plist to select the correct slice for the current build target.

## Swift module interface embedding

Each slice's `Modules/<Module>.swiftmodule/` directory contains the `.swiftinterface` file for that SDK target. This allows downstream Swift users to get full type information and autocompletion when using the XCFramework as a binary dependency (without needing access to the source).

The `.swiftinterface` files embedded in the XCFramework are generated by the same `swift build` invocation used to produce the static archive; they are authoritative for the slice's ABI.

## Binary size impact

A full 5-slice XCFramework (macOS fat + iOS arm64 + iOS sim fat + tvOS arm64 + watchOS arm64) for a moderately sized Mochi library adds approximately 15-40 MB to the distribution. Breakdown:

| Slice | Size (typical) |
|-------|---------------|
| macOS arm64_x86_64 fat | 4-8 MB |
| iOS arm64 | 2-4 MB |
| iOS simulator arm64_x86_64 fat | 4-8 MB |
| tvOS arm64 (optional) | 2-4 MB |
| watchOS arm64_arm64_32 (optional) | 2-4 MB |
| Linux x86_64 (included in zip, not in .xcframework) | 2-4 MB |

The `binaryTarget` approach in `Package.swift` downloads only the slice needed for the build target; a macOS-only build downloads only the macOS slice (SwiftPM decompresses only the needed slice from the `.zip`). This differs from source packages where all source is downloaded; binary targets can be significantly faster for large packages.

## Limitations

- XCFramework production requires macOS and Xcode. CI environments without Xcode (GitHub-hosted Linux runners) cannot produce XCFrameworks; the `--emit-ci` workflow runs the XCFramework build on a `macos-14` runner.
- watchOS and tvOS slices are not produced by default (only macOS and iOS); they are opt-in via `[swift.publish] platforms = [..., { name: "tvOS", version: "16.0" }, ...]`.
- The XCFramework binary target approach does not support Swift Package plugins (SwiftPM plugins run at build time and require source packages). MEP-69's published packages use source packages (with `TargetSwiftLibrary`); the XCFramework path is an optional binary distribution optimisation for consumers who prefer pre-compiled dependencies.
