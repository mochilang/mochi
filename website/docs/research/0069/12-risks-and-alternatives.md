# 12. Risks and alternatives

## Risk register

### R1. `.swiftinterface` textual format stability

The `.swiftinterface` format has been backward-compatible within major Swift versions, but Apple has added new grammar in each minor release (Swift 5.5 added `async`, 5.7 added `any`, 5.9 added macro declarations, 6.0 added typed throws). A `.swiftinterface` file generated by Swift 6.1 may contain constructs the bridge's Go-side parser does not yet handle.

**Mitigation:** The bridge ships a parser version compatibility matrix. Constructs the parser does not recognise are skipped (emitting `SkipReport: unrecognised declaration form`) rather than causing a parse error. The format-version header (`// swift-interface-format-version: 1.0`) is checked; if it changes to `2.0`, the bridge emits a hard error requiring a bridge update. Parser updates follow new Swift major releases.

### R2. Linux Swift ABI instability

Swift on Linux does not have a stable ABI across major releases. A `@_cdecl` export from a Swift 5.10 library is not compatible with a Swift 6.0 binary on Linux (they link against different `libswiftCore.so` versions). This means a Mochi user who upgrades from Swift 5.10 to 6.0 on Linux must re-compile all imported Swift packages.

**Mitigation:** The bridge enforces that all `[[swift-package]]` entries in `mochi.lock` record the same `swift-compiler-version` prefix (e.g., `5.10.*`). A toolchain upgrade on Linux forces a full `mochi pkg lock` re-run and wrapper regeneration. The error message reads: "Swift toolchain version changed from 5.10 to 6.0 on Linux (ABI incompatible). Run `mochi pkg lock --force-retool` to regenerate all Swift wrappers."

### R3. Wrapper package compile times

A wrapper for Vapor (which pulls in swift-nio, swift-http-types, swift-log, and swift-crypto) covers approximately 500 public symbols across 5 packages. Cold `swift build` for the full wrapper tree takes 40-80 seconds on an Apple M2. For CI environments building from scratch, this is the dominant cost.

**Mitigation:** Wrapper static archives are cached in `~/.cache/mochi/swift-deps/wrappers/<wrapper-sha256>/`. GitHub Actions cache (`actions/cache@v4`) should include `~/.cache/mochi/swift-deps/wrappers/` in the cache key. The `--emit-ci` workflow template includes this cache step.

### R4. SPM git resolution latency

`git ls-remote --tags` for a package with thousands of tags (e.g., large monorepos) can take 3-10 seconds per package on a cold network. A Mochi program importing 10 Swift packages may spend 60+ seconds on git tag enumeration.

**Mitigation:** Tag lists are cached keyed by `<remote-url-hash>/<date>` (refreshed daily). The bridge parallelises `git ls-remote` calls across packages (up to 8 concurrent git operations). For SE-0292 registries, the tag list is replaced by a `GET /packages/<name>/releases` API call that returns a JSON list in one round-trip.

### R5. Apple-platform-only packages

Many popular Swift packages contain Apple-SDK-specific types (UIKit, AppKit, Core Data, AVFoundation). These fail to compile on Linux. The fixture corpus deliberately includes cross-platform packages (phases 0-16) and defers Apple-only integration to phase 17 (Objective-C subset).

**Mitigation:** The bridge parses the `Package.swift`'s `platforms:` array and the `#if os(macOS)` guards in the `.swiftinterface` to detect platform restrictions. Packages with no Linux platform entry are marked `apple-only = true` in the lockfile; attempting to build them on Linux produces: "Package Alamofire requires macOS 13.0+ or iOS 16.0+; Linux build is not supported. Add `[swift.platforms] linux = true` and provide a Linux-compatible version of this package to enable Linux builds."

### R6. SE-0292 registry fragmentation

The SE-0292 registry protocol is implemented in SwiftPM but has not been widely adopted by the package ecosystem. The Swift Package Index's registry pilot covers only a fraction of SPI's total index. Many packages are still consumed exclusively via git URLs.

**Mitigation:** The git-tag publish path is the default and requires no registry adoption. SE-0292 registry publish is opt-in. The bridge's `--to=swift-registry` flag gracefully falls back to the git-tag path if the registry endpoint returns a 404 for the package identity.

### R7. Generic explosion

A user who lists 100 monomorphisations for a generic function generates 100 `@_cdecl` symbols and 100 Mochi `extern fn` declarations. Swift compiler codegen for 100 concrete instantiations of a complex generic (e.g., `OrderedDictionary<K, V>`) may add 20-50 seconds to the wrapper build time.

**Mitigation:** The bridge warns when `[swift.monomorphise]` exceeds 30 entries per package. Each monomorphisation entry for a generic struct or class also generates retain/release symbols, compounding the count. The warning message lists the entry count and estimated compile time.

### R8. `@MainActor` isolation deadlock

Functions annotated `@MainActor` in the imported Swift package, when wrapped with `DispatchGroup`-bounded `Task { }`, will attempt to hop to the main actor executor. Since the Mochi main thread is blocked on `DispatchGroup.wait()`, the main actor executor can never run the task continuation: deadlock.

**Mitigation:**

1. The bridge emits `SkipReport` for all `@MainActor`-isolated functions by default.
2. When `[swift.capabilities] main-actor = true` is set, the bridge emits:
   ```swift
   @_cdecl("mochi_Pkg_mainActorFn")
   public func mochi_Pkg_mainActorFn(/* args */) -> /* return */ {
       var result: ReturnType?
       let group = DispatchGroup()
       group.enter()
       Task.detached {
           defer { group.leave() }
           result = await MainActor.run { Pkg.mainActorFn(/* args */) }
       }
       group.wait()
       return marshal(result!)
   }
   ```
   `Task.detached` is used instead of `Task { }` to avoid inheriting the main actor context. `MainActor.run { }` executes the function body on the main actor's executor without requiring the main run loop (it uses the cooperative scheduler's main actor virtual executor).

### R9. Swift macros are invisible to the bridge

Swift macros (SE-0382, Swift 5.9) are compile-time code generators that expand into Swift source; they do not appear as callable items in `.swiftinterface` files with a stable ABI entry point. A package like `swift-observation` (`@Observable` macro) or `SwiftData` exposes its primary API through macros.

**Mitigation:** The `SkipReport` documents macro-only items. The bridge notes the expanded form where it can be determined from the `.swiftinterface` (the expanded types appear in the interface even if the macro that generated them does not). For packages primarily used via macros (SwiftUI views), the Objective-C subset path (phase 17) provides an alternative through Objective-C bridging.

### R10. XCFramework binary size for multi-platform

A 5-slice XCFramework for a large Mochi library can reach 40+ MB. CI artefact storage and download times are affected.

**Mitigation:** Apply `-Osize` optimisation level for XCFramework builds (default for MEP-69 XCFramework builds, overridable via `[swift] optimization = "speed"`). Offer thin-slice XCFrameworks that include only the slices the user declares in `[swift.publish] platforms`.

### R11. Linux static stdlib size

A Linux binary statically linked with the Swift standard library (`-static-stdlib`) adds approximately 30-50 MB to the binary size. For small CLI tools, this is disproportionate.

**Mitigation:** The bridge applies `-static-stdlib` only for executables on Linux (not for library targets). Users who need smaller binaries can opt out via `[swift] static-stdlib = false` and ship the Swift standard library as a separate artifact (requiring the target to have the Swift runtime installed).

### R12. Git-tag mutability

Git tags can be overwritten (`git push --force`), breaking reproducibility: a locked `mochi.lock` that pins `Alamofire@5.9.1` at commit `abc1234` may find that the live `5.9.1` tag now points to a different commit.

**Mitigation:** `mochi pkg lock --check` re-fetches the commit SHA for each pinned tag and compares it with `source.commit` in the lockfile. If the commit SHA has changed, the check fails with: "Tag 5.9.1 for Alamofire was overwritten: expected commit abc1234, found def5678. Run `mochi pkg lock --force-update` to accept the new commit." The SE-0292 registry path is immutable (registries reject overwrites); users who need immutability guarantees should prefer SE-0292 registry dependencies.

## Rejected alternatives register

### A1. Parse Swift source directly

Rejected. See [[02-design-philosophy]] §1 and [[04-swiftinterface-ingest]] §1 for the full argument: Go-side Swift parser would be 40,000+ LOC; `#if` conditional compilation defeats source-level parse; Swift macros are not visible in source.

### A2. Use swift-syntax (Apple's Swift syntax library)

Rejected. `swift-syntax` parses source (same `#if` problems); requires a Swift runtime on the bind host; output format is not versioned for programmatic consumption. See [[02-design-philosophy]] §1.

### A3. Use SourceKit-LSP as the bind source

Rejected. Interactive-editor latency (5-15 sec startup per package); output schema not versioned; schema can change across Xcode releases without a stable interface-format-version header. See [[02-design-philosophy]] §1.

### A4. Use swift-bridge for the FFI layer

Rejected. `#[swift_bridge::bridge]` hand-annotation required per item; violates the "no boilerplate" promise. swift-bridge is the right tool when the author controls both sides; MEP-69 generates bindings from existing packages without modification. See [[03-prior-art-bridges]].

### A5. Use UniFFI (Mozilla) for the binding layer

Rejected. Requires a UDL interface description file authored by the user; same boilerplate-violation argument as swift-bridge. See [[03-prior-art-bridges]].

### A6. Use Objective-C bridging as the primary mechanism

Rejected. Requires classes (no value types), Apple platform only (no Linux), excludes modern Swift packages (swift-nio, swift-collections). `@_cdecl` is universal and works on Linux. See [[02-design-philosophy]] §2.

### A7. Use WIT (WebAssembly Interface Types) as the bridge protocol

Rejected for v1. Swift Wasm Component Model support is experimental (swift-wasm); MEP-69 targets native Swift packages. A v2 could add a `--mode=wit` flag for swift-wasm component consumers.

### A8. Require `@_cdecl` annotations on the source package

Rejected. Same boilerplate-violation argument. The user would have to modify every upstream Swift package they import to add `@_cdecl` annotations. MEP-69 synthesises those annotations in the wrapper package without modifying the source.

### A9. Use `dlopen` of pre-built Swift `.dylib` artefacts

Rejected. Swift `.dylib` on Linux is ABI-version-specific; crates.io / SPM do not host pre-built binaries; feature/target combinations make pre-built binaries non-universal. Source-compile-and-static-link is the universal path. See [[09-abi-stability]].

### A10. Use `@_expose(Cxx)` instead of `@_cdecl`

Rejected for the primary path. `@_expose(Cxx)` generates C++ headers (SE-0297), not C headers. The bridge's C sidecar pattern (MEP-45) uses C ABI. `@_expose(Cxx)` is noted as a future optimisation for the XCFramework C++ header path.

### A11. Support long-lived SE-0292 registry API tokens as the default

Rejected. Matches MEP-57's principle. The SE-0292 registry publish path uses GitHub Actions OIDC where supported. Long-lived tokens are accepted only as a fallback (logged as a warning) for registries that do not yet support OIDC.

### A12. Auto-monomorphise all possible generic instantiations

Rejected. Combinatorially explosive (a package like `swift-collections` has 100+ generic combinations). The `[swift.monomorphise]` table makes the surface bounded and user-visible. The bridge warns when the table exceeds 30 entries per package.
